# 3.4 Line drawing

Code: `src/natives/line.c`, shared header `src/natives/raster.h`.

## Natives

| Native | Address | Calls (campaign) | Mismatches | `.cycles` | Flags |
|---|---|---|---|---|---|
| `draw_line` | 0050:5691 | 93,762 | 0 | 1400 | none |
| `draw_line_list` | 0050:408F | 379 (war only) | 0 | 12300 | none |
| `draw_horizon_list` | 0050:408C | 102 (user_mode_3 only) | 0 | 7109 | none |

`python3 tools/verify_campaign.py` prints OK with all three enabled. The polygon path (5060, below)
runs inside `draw_line` and was covered in user modes 1 to 5 (thousands of calls, 0 mismatches).

- **Cycles.** The original `draw_line` costs between 283 cycles (1 pixel) and 11,825 cycles, about
  283 + 72 per extra pixel. The mean line in the campaign is 16 to 18 pixels, so `.cycles` is 1400.
  The two list routines draw fixed shapes in the campaign: 12,300 cycles for the war-mode lines and
  7,109 for the horizon outline.
- **Flags.** Nothing relies on them. `draw_line_list` callers overwrite them (`xor ax,ax` and the
  scenery VM loop). `draw_horizon_list` is reached through `call cx` in `scenery_interp` (opcode 15)
  and from `draw_sky_ground` (2B09), and both overwrite them. The tail call at 4DC3 returns into
  `clip_project_line` callers, which also overwrite them.
- **Stack words.** The polygon path CALLs helpers, so the original writes their return addresses
  below SP. `--verify` compares those bytes. The natives therefore write the same words (via the
  `RasterBus.call` hook): at SP-2 for `draw_line`, and for the list routines 40B9 at SP-2 with
  `draw_line`'s helper calls at SP-4.
- **Registers on return.** All registers are as the original leaves them. That includes DS = the
  back buffer segment and ES = the game DS from 0000:0120. On the polygon path's early exit, BP is the
  helper's return address, because the original does `pop bp` and then `ret`.
- `draw_line_list` calls the C rasteriser directly. `draw_horizon_list` is the 3-byte stub
  `mov ax,041F` that falls into `draw_line_list`, so it is a separate native. If only
  `draw_line_list` is enabled, the trap at 408F still works, because the stub pushes nothing.

## Rasterisation (normal path, 569B)

The coordinates are fat pixels: x 0..159, y 0..105. The byte for (x, y) is `row[y] + x/2`, where
`row` is the word table at DS:380C (even rows at +0000, odd rows at +2000, 80 bytes per row). Even x
is the high nibble, set to `[30C9]`. Odd x is the low nibble, set to `[30C8]`. The nibbles are
already in position: `draw_colour` 8008h means high 80h and low 08h. There is no clipping.

1. Order the endpoints so that x0 <= x1. If x0 > x1, both points are swapped.
2. **Vertical** (x0 == x1): sort by y, then draw y1−y0+1 pixels downward.
3. **Horizontal** (dy == 0): draw dx+1 pixels to the right. When two pixels share a byte, the byte is
   written once.
4. Otherwise it is Bresenham, with dx = x1−x0 > 0 and dy = y1−y0:
   - **x-major** (|dy| <= dx; a 45° diagonal counts as x-major). `err = dx >> 1`. Repeat dx+1 times:
     plot (x, y); `err −= |dy|`; if `err <= 0` then `y += sign(dy)` and `err += dx`; `x++`.
   - **y-major, dy > 0.** `err = dy >> 1`. Repeat dy+1 times: plot; `err −= dx`; if `err <= 0` then
     `x++` and `err += dy`; `y++`.
   - **y-major, dy < 0.** The original keeps a negative error and starts it at `sar(dy)`, which rounds
     down. So the equivalent positive error starts at **ceil(|dy|/2)**, not floor. Repeat |dy|+1
     times: plot; `e −= dx`; if `e <= 0` then `x++` and `e += |dy|`; `y−−`. This asymmetry is real.
     Lines going up step x one pixel earlier than mirrored lines going down.

The code is unrolled by row parity (even/odd bank) and nibble (high/low), with row steps +2000h,
+E050h (−1FB0h), +1FB0h and +E000h. It keeps a pending high nibble in AL, so that when the next pixel
is in the same byte, the byte is written once. The native is a label-for-label translation of that
code (labels `Lxxxx` = 0050:xxxx), so the memory writes and the final registers match exactly.

## The alternate path at 5060: filled-polygon outlines

`[31D0]` is the **polygon mode** flag:
- Scenery opcode **2F** (`op_poly_begin`, 44FB) sets it and empties the seed list at DS:3730.
- Opcode **2D** (`op_poly_end`, 5468) clears it and terminates the list. If `[0412] & 1` and the
  view is not radar, it then calls `poly_fill` (549B).

While the flag is set, every `draw_line` (the opcode 02/29 line-to edges) takes the 5060 path. This
path draws the same Bresenham line, with these differences:
- **x is clamped.** x == 0 becomes 1 and x == 159 becomes 158, on exact equality only. This keeps
  the outline off the view's side edges.
- **Endpoint order.** The swap happens when x0 >= x1, so x0 == x1 also swaps. The swap is recorded in
  `P_SIDE` (0C0C:1F45, see below). A vertical line goes through the general code, as y-major.
- **Inside side.** Y-major lines going up flip `P_SIDE` (53C6). After this, `P_SIDE` says which side
  of the edge is inside.
- **Midpoint seed.** In a line of more than 3 pixels (count n = major+1 > 3), the pixel at number
  ceil(n/2) is **not drawn**. Instead it is recorded as a fill seed (53D3 sets this up, and the
  helpers 53EC/53FE/5410/5422/5440/544A run when the count reaches 0). The rest of the line is drawn
  normally. The last pixel is drawn by the same helpers. They then leave `draw_line` with `pop bp; ret`.
- **Seed record.** Each seed is appended to `poly_seeds` (DS:3730 holds the byte index; records are
  at 3734+i) as {neighbour, pixel}:
  - pixel = byte address, with bit 15 set if it is the high (left) nibble.
  - neighbour = the pixel on the inside: the row above or below for x-major edges, the nibble to the
    left or right for y-major edges. It carries the same bit-15 nibble flag.
  - An x-major seed whose neighbour would be above row 0 or below row 105 is not recorded. The
    midpoint pixel is still left out.

`poly_fill` (549B) then uses the list:
1. It removes duplicate seeds and plots the seed pixels themselves (OR 0F/F0).
2. It drops neighbours that are already set.
3. It flood-fills from the remaining neighbours with `sub_59B7`, a span fill that replaces colour
   `[31CE]` with `[3159]`.

So the 5060 path is "draw a polygon edge and leave a gap with a seed for the fill". It is not XOR,
and it is not a pattern.

**Scratch bytes in the back buffer segment.** The 5060 path runs with DS = the back buffer segment,
so the `[1F44]`..`[1F49]` accesses the disassembly labels `enemy_table+9..14` are **not** the enemy
table. They are bytes at 0C0C:1F44..1F49, in the unused gap after bank 0's 106/2 rows (bank 0 ends
at 1090h):

| Offset | Name in line.c | Meaning |
|---|---|---|
| 1F44 | `P_MID` | 1 while the midpoint is still ahead |
| 1F45 | `P_SIDE` | inside side |
| 1F46 | `P_FLAG` | 8000h if the seed is a high nibble |
| 1F48 | `P_HALF` | pixels left after the midpoint |

## The reusable rasteriser (`src/natives/raster.h`)

```c
typedef struct RasterBus {
    void *ctx;
    uint8_t (*buf_rd)(void *ctx, uint16_t off);          /* back buffer segment ([3806]) */
    void (*buf_wr)(void *ctx, uint16_t off, uint8_t v);
    uint8_t (*dat_rd)(void *ctx, uint16_t off);          /* game data segment (0618) */
    void (*dat_wr)(void *ctx, uint16_t off, uint8_t v);
    void (*call)(void *ctx, uint16_t ret_ip);            /* optional: internal CALL return words */
} RasterBus;
typedef struct RasterRegs { uint16_t ax, bx, cx, dx, si, di, bp; } RasterRegs;

void raster_line_regs(const RasterBus *b, RasterRegs *r);      /* 569B normal path */
void raster_poly_edge_regs(const RasterBus *b, RasterRegs *r); /* 5060 polygon path */
void raster_line(const RasterBus *b, int x0, int y0, int x1, int y1); /* picks by [31D0] */
```

- `buf_*` covers the pixels and the polygon scratch bytes 1F44..1F49.
- `dat_*` covers the row table 380C, the colours 30C8/30C9, the flag 31D0 and the seed list 3730.
- `call` may be NULL outside the emulator.
- The scenery interpreter (3.8) can call `raster_line` directly. For a phase-4 renderer, use the
  algorithm description above, or a bus over a plain 16 KB array.

## Screenshots: natives on and off

Command: `--native-off all` against the default, same frames. I compared the BMPs byte by byte, and
visually where they differed.

| Case | Result |
|---|---|
| Regular view (demo 1500/3000/4500/6000, display_A 700/1000/1200) | small differences |
| User mode 2 (800 and the final frame) | identical |
| User mode 2 (1400) | small differences |
| User mode 3 (800, 1400, final) | small differences |
| Radar view (Num Lock; 800/1100/1400) | small differences |
| War (1300/1700/2500/3500/4660) | small differences |

All the differences are timing. `draw_line` charges a fixed 1400 cycles, while the original costs
283 to 11,825, so the emulated timeline drifts. The result is a different frame phase:
- the compass shows 309 against 308
- war-mode enemies are a pixel or two apart
- radar ground tracks are slightly shifted

The images otherwise look the same: same scenery, horizon, filled shapes and lines. `--verify` shows
that every call writes the same bytes as the original.

## New symbols (symbols.txt syntax)

```
code 0050:5060 draw_poly_edge        ; [code] draw_line while [31D0]: x clamped 1..158, midpoint pixel left out and stored as a fill seed
code 0050:532C poly_seed_xmajor      ; [code] seed with the neighbour in the row above/below (also 5345)
code 0050:5372 poly_seed_ymajor      ; [code] seed with the neighbour nibble left/right (also 53AC)
code 0050:53C6 poly_count_up         ; [code] y-major going up: flip inside side, then poly_count
code 0050:53D3 poly_count            ; [code] BP = pixels+1; > 3 -> stop at the midpoint first
code 0050:44FB op_poly_begin         ; [code] scenery opcode 2F: [31D0] = 1, empty poly_seeds
code 0050:5468 op_poly_end           ; [code] scenery opcode 2D: [31D0] = 0, end list, poly_fill if [412]&1 and not radar
code 0050:549B poly_fill             ; [code] plot seeds, drop set neighbours, flood fill from the rest (sub_59B7)
var 0618:31D0 poly_mode byte         ; [code] nonzero: draw_line records polygon seeds (path 5060)
var 0618:30C4 line_list_ptr word     ; [code] draw_line_list record pointer
var 0618:3730 poly_seeds table       ; [code] word byte-index, then {neighbour, pixel} word pairs from 3734; bit 15 = high nibble
```

Also:
- Scenery opcode **15** is `draw_horizon_list` (408C). It draws the captured `horizon_list` at 041F.
- The `enemy_table+9..14` names at 1F44..1F49 are wrong inside 5060..5467 (DS = back buffer
  segment there). The listing would need per-routine segment awareness to show this.
