# 3.16 Editor, presets, menus

Natives in `src/natives/editor.c` (27 entries). The cycle table `src/natives/editor_cycles.h`
is generated by `tools/gen_editor_cycles.py`. Coverage sessions are in `tools/editor_sessions.py`.

Everything that ends with a RET is now native:
- the editor's field, page and cursor routines
- the user-mode presets
- capture and apply of the flight state
- the start-up disk check
- the `'*'`, Insert, Enter, `=`, `-` and Esc key handlers

The three loops that wait for a key stay original, because `--verify` cannot handle them (see
"Not replaced"):
- `editor_main` 3640
- `editor_get_input` 3703 (its key loop, start, digit entry and dispatch)
- `startup_menus` 5CE9

Backspace, `s` and `l` are natives that continue in the key loop instead of returning.
- `s` and `l` save and load the presets to a host file instead of disk track 26h.
- None of the three can be checked by `--verify`. They are checked by comparing runs with the
  natives on and off.

### How the natives are written

**Registers and memory.** Each native is transliterated on the emulated registers and leaves
every register, every stack word written by CALL or PUSH, and every memory byte as the original
does. Variables go through the generated `gs_*` accessors with the live DS. `usermode_recall`,
`editor_apply_state` and the disk check also run at start-up, where DS is 0686.

**Calls.** `call(pc, at)` decodes the original's CALL at `at` and pushes the return address.
It then runs the target as the CPU would with the natives on:
- another enabled native (this file, 3.2 `editor_digits_to_bin` / `editor_bin_to_digits`,
  3.11 `clock_hm`, 3.17 `war_score_add` / `war_ground_reset`, ...) runs through `native_call()`;
- anything else (`cga_program_regs`, `sub_0955`, `sub_0D01`, the boot-sector disk code) is
  single-stepped.

**Cycles.** Cycle accounting is exact.
- `run(from, to)` adds the cpu8086.c cost of each original instruction on the path taken.
- The costs come from `editor_cycles.h`. `tools/gen_editor_cycles.py` builds that table by
  single-stepping every instruction of the ranges on `src/cpu8086.c` with forced flags and CX
  values.
- `FS1_EDITOR_CYCLE_CHECK=1` is a debugging aid. Before each call it single-steps the original
  with an undo log and compares the cycles, logging `cycle-check NAME: original N native M`.
  All 36 sessions (`editor_sessions.py shots`, with and without `CAMPAIGN=1`) log no differences.

**DIV overflow.** Apply converts wind knots with `div cl`. A typed wind of 25600 or more knots
overflows the DIV, and capture's `div cx` overflows the same way. The original takes INT 0,
whose handler at 0050:4DC6 sets AX = 7FFFh, or 8001h when DX XOR BX is negative. For that
case only, the native single-steps the original's DIV and handler. The `wind_overflow` session
covers it.

### Interrupts (hand-back)

The timer interrupt and the natives share state:
- **Flight state.** `flight_forces` runs inside the timer interrupt, which capture reads and
  apply writes.
- **Sound and ATIS fields.** The timer handler reads [2049] and [204F], which recall and
  commit write.
- **Clock.** The timer handler increments clock_min / clock_hour.
- **Merged ticks.** A native holds interrupts until it returns. When more than one timer tick
  falls due inside one native step, `pc.c` delivers the extra ticks back to back. A tick that
  falls due meanwhile merges into a pending one. The `user_modes` session showed this: the
  timer phase drifted although every screenshot matched.

So every returning native does this (`entry_run`):
1. It runs with an undo log (the CPU write log).
2. If the timer or the keyboard would have interrupted within its cycles, it undoes its memory
   writes and restores the CPU.
3. It then performs the original's first instruction and lets the CPU continue in the
   original, with interrupts.

This is the same approach as 3.14's `irq_hand_back`. A few more details:
- Port writes (CGA registers, port 61h) are simply repeated by the original with the same
  values.
- Natives nested in one that keeps the log run plain, so the outermost one decides.
- Under `--verify` nothing is handed back.

How often the natives ran instead of handing back, over all 36 sessions:

| Native | Ran natively |
|---|---|
| `row_ptr`, `field_next`, `scale_wind`, `alt_from_editor`, `key_accept`, `key_up`, `next_row` | 95-99% |
| `speaker_off`, `check_master_disk` | 100% |
| `prev_row` | 89% |
| `apply_state` | 71% (start-up calls run under the slow BIOS timer) |
| `usermode_store` / `usermode_recall` | 58% / 31% |
| `scale_values` (called alone) | 29% |
| `capture_state` | 14% (the scripts press Esc at a fixed timer phase) |
| `commit`, `draw_fields`, `read_fields`, `first_page`, `page_text`, `draw_page`, `key_star`, `key_ins` | 0% |

The last row needs explaining:
- Each of those natives takes longer than one timer period (about 20,000-25,000 cycles at
  normal RPM). For example, `commit` takes about 135,000 cycles.
- So in play they always hand back, and the original then calls the short natives inside
  them, which mostly run natively.
- They still run natively under `--verify`, which checks them as whole units.
- They would run natively in play only with interruptible natives (see "Framework notes").

## Not replaced

`editor_main` (3640), `editor_get_input` (3703) and `startup_menus` (5CE9) poll `editor_key`
until the keyboard interrupt sets bit 7.
- `--verify` single-steps the original without interrupts until it returns, so from any address
  inside these loops it would hit the 5,000,000-step cap.
- That counts as a mismatch and stops verification of the entry. The campaign reaches all three
  (every editor session, every start-up), so such an entry would make `verify_campaign.py` fail.
- The framework has no way for a native to decline a call or to stop verification at a loop
  head. `native.c` cannot be changed in a subphase.

What is bound around the loops instead:
- **In `editor_main`:** the routines it calls (capture, page, rows, commit, apply).
- **In `editor_get_input`:** the handlers that end in a RET:
  - 374E: Enter, `=`, Esc
  - 3740: `-`
  - 37D4: `'*'`
  - 37DD: Insert (editor key 11h)
- **Handlers that jump back into the key loop**, bound as non-returning natives (`IP` = 3726, or
  3643 for the redraw):
  - Backspace (3756)
  - `s` (379A) and `l` (37B5)

  Digit entry (3803..3853) also jumps back, but the campaign types digits, so binding it would
  fail the gate. Digit entry stays original.
- **In `startup_menus`:** only `check_master_disk`, which it calls.

### Start-up code in the init area (5C80+)

`check_master_disk` 629C is bound in the one-time init area. That is safe:
- The dispatch matches CS:IP only (CS = 0050, IP = 629C) and does not look at the code bytes.
- After start-up, 0050:5C80+ becomes data (DS 0618:0000+). The program never executes there
  again, so the hook is never reached by data.
- A Ctrl+Alt+Del reboot reloads the code, and the hook works again (campaign `reboot` session:
  2 calls, verified).

The disk-backup path (5F54, 62D2, 631C ...) stays original. It runs with a disk image whose
track 1Ch byte 0 is patched to 1 (master), started with `120:A,180:C`. It shows "the copy disk
should be in the drive" and waits for a disk swap that cannot happen with one image. It does
not crash, and runs identically with the natives on and off (screenshots and final state
compared).

## Presets: `s` / `l` and the host file

The preset area is DS:2916..30B3: 79Eh = 1950 bytes, 30 slots of 41h bytes. `s` saves it all
and `l` loads it all.

**File.** The file `fs1_presets.bin` holds exactly these 1950 bytes, raw. Where it lives:
- **Environment override.** `FS1_PRESETS` (a full path) overrides the location. The test tools
  use it, one file per run.
- **Saving.** The game writes next to the executable (`SDL_GetBasePath()`, e.g.
  `build/fs1_presets.bin`). If that fails it writes to `SDL_GetPrefPath("fs1-sdl3",
  "Flight Simulator 1")`.
- **Loading.** The game reads the file next to the executable first, then the one in the
  preference folder. A file of another size is ignored, with a log line.
- **Logging.** Each save and load logs `editor: presets saved to / loaded from PATH`.

**Memory after `s`.** Memory ends as after the original's successful track write:
- B800:0000..079D hold the presets (the original's stream buffer).
- `stream_pos` = FFFF, `disk_track` = 27h.
- The `format_table` tracks = 26h, `track_verify` = 0, `disk_dx` = 0.

The emulated disk image is not written. The original would have written track 26h of the
in-memory image, which was never saved anyway.

**Memory after `l` with a file.** As after a good read of the track:
- B800:0000..079D and the presets hold the file.
- `disk_track` = 27h, `stream_pos` = 079D.

**`l` with no file.** This behaves as the original does with an unformatted track 26h:
- `boot_read_track`'s INT 13h fails, so `disk_error` = 1 and `disk_track` stays 26h.
- `boot_stream_byte` still returns the bytes of the track buffer B800:0000..079D. That is the
  editor's text page, as character and attribute 0Fh pairs.
- So the presets become screen bytes. Recalling a user mode then gives garbage values, for
  example "3872" = 0F20h in many fields, slew on and odd positions, as in `load_no_file`.
- Nothing crashes. `s` writes a good file again.

**After either key.** Both finish as the original does:
- `pop ax`, then `sub_016B` (drive motor off).
- Then the redraw at 3643. The CGA registers were set by `cga_program_regs` first, as in the
  original.

**Cycles.** `s` and `l` charge the original's cycles for its disk code on the matching path:
- **`s`:** the stream copy, format, write, read-back and two 800h-word checksums (INT 13h =
  INT + the BIOS stub `0F nn` + IRET).
- **`l`:** the stream copy and one track read, good or failed.

So the timeline after `s` / `l` is the original's (`save_load` session: identical final state).

**--verify and host I/O.** The two natives continue into the redraw and key loop at 3643, so
`--verify` cannot run them: it would hit the step cap. Ignore ranges would not help.
- They are not reached in the campaign.
- `editor_sessions.py verify` leaves them (and Backspace) out by default.
- They are checked by `editor_sessions.py ab`, natives on against the 3.16 natives off:
  - natives on: the file;
  - natives off: the emulated track write and read.
  - Session `save_load` (save, change slot 12, load, recall 12) gives identical screenshots and
    identical final memory and CPU state.
- `editor_sessions.py persist` checks that presets survive a restart. Run 1 stores altitude 4321
  in user mode 12 and saves. Run 2, a new process, loads and recalls mode 12, and gets 4321.

## Findings

- **Field tables (runtime).**
  - `editor_field_lists` 208E = {2092, 20CF} for page 0 and page 2. `editor_page` is 0 or 2,
    a byte offset into the table.
  - Records are {width 1/2 bytes, row, offset from 2049}, ending with 0.
  - `editor_page_texts` 2110 = {2114, 24FC}: 1000-character pages.
  - `editor_row_offsets` 28E4 holds a text offset (32h, 82h, ... 762h) per row. Rows are byte
    indexes 2..2Ch, two per screen line, not doubled.
  - Page 1 has 20 fields: the user mode at 208A, then 2049..204F, then N/E/alt/pitch/bank/
    heading/speed/throttle/rudder/ailerons/flaps/elevators.
  - Page 2 has 19 fields: time, season, cloud layers, three wind levels with shear zones, the
    surface wind, and reliability (2089).
- **Enter on row 2Ch** flips to the other page. `-` on row 2 flips to row 2Ch of the other page
  (wrapping from page 0).
- **Typing a user mode keeps the cursor on row 2.** After the commit, `editor_main` skips
  `editor_next_row` when page = 0 and row = 2.
- **User mode field rules** (`editor_commit`):
  - 0-9 recalls the slot.
  - Entering the current mode again stores the editor values into slot n+10, and the field
    shows n+10.
  - 110-129 stores into slot n-100 (10..29).
  - 30..109 and values above 129 count as 0.
- **Insert** (scan code 52h, editor key 11h):
  - With a user mode below 10 it acts as "typed" (`editor_main` commits, so the store goes to
    n+10).
  - Otherwise it stores the values into the current slot.
- **`'*'`** (Keypad `*`) recalls the current user mode into the editor.
- **Backspace with no digits typed** does nothing.
- **Esc after a 3+-digit Pitch / Bank (reported by 3.5).** Not reproduced.
  - Variants tried with all natives off:
    - pitch or bank of 100, 123, 270, 359, 360, 999, 1000 and 12345;
    - with and without Return, with slew on, with altitude 3000 first;
    - entering the editor again afterwards.
  - Every one left the editor (CGA mode 1Ah afterwards), and the same sessions behave
    identically with the natives on (`pitch_123`, `bank_123`).
  - The editor's key loop is still the original code, and every native is verified. Whatever
    produced the report is therefore kept exactly as the original has it.
- **`editor_apply_state` with war mode on** first recalls user mode 7.
- **`[202A]`** (`apply_phase`) = (frame_counter & 1Fh) - 10h, set on every apply. It is read at
  4FCE (ATIS text).

## Gate

- **Campaign verify.** `python tools/verify_campaign.py` prints OK with all natives enabled.
- **Session verify.** `python tools/editor_sessions.py verify` prints OK: 0 mismatches for every
  native of every area in the 22 sessions.
- **Calls.** Every 3.16 native has nonzero calls in the campaign or the sessions. The three
  non-returning ones are compared with `ab` instead.
- **Build.** A clean rebuild (`cmake --build build --clean-first`) has no warnings.
  `python tools/gen_state.py --check` passes.
- **Screenshots.** `editor_sessions.py ab` prints OK for all 22 sessions and for the 14 campaign
  sessions (`CAMPAIGN=1`), 185 screenshots in all:
  - the editor screenshots, the flight screenshots and the final memory are byte-identical,
    natives on against the 3.16 natives off;
  - so are the CPU position and cycle count at the end.
- **Cycles.** `FS1_EDITOR_CYCLE_CHECK=1` logs no differences.

## Framework notes (for the coordinator)

- **Key-waiting loops.** Binding the key-waiting loops (`editor_main`, `editor_get_input`, the
  digit entry and `startup_menus`) needs two things in `native.c`:
  1. A way for a native to decline a call (for example `NativeFn` returning bool), so that the
     original's wait loop runs while no key is pending.
  2. A per-entry `verify_stop` address: `--verify` would also end the original's run when IP
     returns to the loop head (3726, 5CFC, 5D68) with the entry's SP.

  With these, a native at 3726 could handle one key and be verified per key.
- **Interruptible natives.** Long natives (`editor_commit`, `editor_draw_fields`, ...) hand back
  whenever a timer tick falls inside them. They could run natively if the framework could
  deliver an interrupt inside a native at the original's instruction boundary. The table-driven
  cycle accounting here already knows the original IP at every point. What is missing is a
  `pc.c` helper that advances the PIT by n cycles (`pit_advance` is static), and a way to resume
  the native after the handler.
- **Shared helpers.** `irq_due()` / `entry_run()` here and 3.14's `irq_hand_back` do the same
  thing. A shared helper in `native.h` would avoid the copies.
