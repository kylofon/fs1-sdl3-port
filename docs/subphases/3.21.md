# 3.21: main loop and timer in C

The main loop (0050:01F8-02CA) now runs as native code. So do the remaining routines on the frame's
hot path and the polling loops. During normal flight the 8086 core executes about 25 original
instructions per frame, against about 5,000 with every native off. What still runs as original
code is listed below with the reason for each. The emulated PC is unchanged: video RAM, PIT/PIC,
ports and the BIOS data area are untouched (removing them is 3.22).

## Measuring: `--stats`

`fs1 --stats` counts the original (non-native) instructions the CPU executes. It does this with a
per-address counter in `cpu_step`, which is skipped for steps a native handles. On quit it prints
the total, the number of native calls and the hottest addresses.
- `--stats-from FRAME` starts counting at that frame.
- `--stats-out FILE` writes every executed address as `LINEAR COUNT` lines.
- `python tools/insn_stats.py [SESSIONS] [--from F] [-- ARGS]` runs campaign sessions with these
  options (default `--from 300`, after the start-up menus) and totals the counts per routine, using
  the labels in `extracted/fs1.asm`.

Original instructions executed from frame 300 to the end of each session:

| war (4,360) | 22,929,257 | 2,218,401 | 88,068 |

### The main loop

The loop never returns, and it calls about 40 routines per frame. Some are long natives (scenery,
blit) and some are original code. If one native ran the whole iteration, it would hold the timer
interrupt for a whole frame, so the loop is split into blocks instead:
- One C function, `n_main_loop`, is bound at the loop head and at each return address of a CALL in
  the loop.
- It runs the loop's code from there to the next CALL, which it performs: it pushes the return
  address and sets IP to the callee. Or it runs to the loop head.
- Each callee runs as its own CPU step, exactly where the original calls it. Interrupts are taken
  between the steps, as with the original.

The C code follows the original's control flow (`plan_block`):
- the editor branch, with `editor_active` cleared after `blit_view_to_screen`;
- the `timer_hooked` test. When it is 0 the block ends at 0211, and the original `JMP $` hangs,
  as in the original;
- pause. Each pass returns to 01F8;
- slew or flight;
- the plain call chain;
- the 4-phase dispatch on `frame_counter` (AX/AL as the original leaves them for the callees),
  `blink_bits` and `frame_counter++`.

### Timing: declining instead of handing back

Each new native first works out the cycles the original would take, without writing anything. It
uses the table `mainloop_cycles.h`, generated by `tools/gen_mainloop_cycles.py` from the cpu8086.c
cost model. It then asks `pc_irq_horizon()` how many cycles the step may last:
- If the timer, the keyboard latch or the end of the front-end frame falls inside, the native
  declines and the CPU runs the original from that instruction, with interrupts.
- Otherwise it runs and charges exactly the original's cycles.
- The loops run as many whole passes as fit before the horizon, and decline for the last one.
  These are the paused main loop, the key waits, the crash delay and the two resumable loop bodies.

This replaces the undo-log hand-back of earlier subphases. Nothing is undone, because nothing has
been written yet.

When `draw_view_frame` or `view_overlay_marks` decline, the original runs only their short head.
It then reaches the loop natives at 5AC9 and 0700, so a decline costs about 15-25 original
instructions instead of the whole routine.

## Framework changes

All are opt-in. Existing natives behave as before.

- **`NativeEntry.try_fn`** (`bool (*)(Pc *)`) is used instead of `fn` when set. Returning false
  declines: nothing may have been changed, and the CPU executes the original instruction. The
  decline is counted in `declines`, and `--verify` prints it as `declined N`.
  `native_call()` returns false on a decline.
- **`stop_lo`, `stop_hi` and `stops`** are for natives that do not return. Under `--verify` the
  original runs until, after at least one instruction, CS:IP leaves `GAME_CS:[stop_lo, stop_hi)`
  or reaches an address in `stops` (a 0-terminated list), instead of until it returns. The main
  loop uses `[01F8, 02CB)` with stops {01F8, 0211}, so the verified unit is one block. A loop
  native does exactly one pass while `native_logged(pc)` (verify, or nested under a write log).
- **`exact_cycles`.** `--verify` also compares the cycles the native charges with the original's.
  It caught a missing RET cost in `view_overlay_marks`.
- **`pc_sync_pit(pc)`** (pc.c). pc.c now remembers how far the PIT has been advanced
  (`pit_synced`), and `pc_run` advances it by the rest of the step after each step. A native calls
  `pc_sync_pit` before it reprograms a PIT channel, so the new count starts at the right cycle.
  **The 3.19 workaround in sound.c that wrote `pit[n].count` directly is removed.** `out_at` now
  syncs before any write to ports 40h-43h. The PIT count comes out the same as with the old workaround.
- **`pc_irq_horizon(pc)`** (pc.c). This is the number of cycles the current step may still run
  before an interrupt could be raised at an earlier instruction boundary, or before the frame
  (`pc_run`'s target, now `run_target`) ends. It is 0 when an IRQ or an IRQ0 backlog tick is
  pending. It is conservative: IF and the masks are ignored.
- **`--stats`** (main.c, plus the `exec_count` pointer in `Cpu8086`, a 3-line change in
  cpu8086.c/h).
- The IRQ0 backlog (2ee6d79) is unchanged.

`pit_synced` and `run_target` lie inside the device-state range that `--verify` and the hand-back
code snapshot (`pic_irr` .. `speaker`), so they are restored with the PIT.

## Timer

`int8_timer` was handed back to the original on most calls: about 26,500 of 30,000 in flight_keys.
The reason was that `irq_due()` treated any IRQ0 backlog, or any timer tick due within the
handler, as an interrupt inside it. A backlog of tens of ticks is normal: long native steps
create it. But the handler runs with IRQ0 in service (ISR bit 0) and IF clear until its IRET. A
tick that falls due inside it is raised and delivered after the IRET, exactly as with the
original. So does a backlog tick, which the original moves into the IRR right after the EOI.

`entry_run` now ignores the timer for `int8_timer` called as IRQ0 with IF clear, except in two
cases:
- two ticks fall due inside it;
- one falls due while the backlog is nonzero. With the original, that tick merges into the backlog
  tick already moved to the IRR.

The keyboard latch (`kbd_next_cycle` depends on step boundaries) and `if_at_eoi` still hand the
call back. Original instructions in `int8_timer` dropped from 576k to 31k in flight_keys.

Interrupt latency inside long natives (3.3/3.14/3.20) is addressed for the new natives only, by
declining. The older natives (`print_str_mask`, `flight_integrate`, `upd_obi`, the editor ones,
...) still hand back the whole call. Making those resumable is the remaining work.

## Symbols

```
code 0050:063C crash_delay ; [code] crash_handler: 65535 x (3 MUL CL), LOOP
code 0050:0700 overlay_rows ; [code] view_overlay_marks: one filled span per row
code 0050:5AC9 view_frame_loop ; [code] draw_view_frame: OR F0h into the left border, 54 line pairs
code 0050:3726 editor_wait_key ; [code] editor_get_input: wait for editor_key bit 7
code 0050:5CFC menu_wait_key1 ; [code] startup_menus: wait for editor_key bit 7 (display menu)
code 0050:5D68 menu_wait_key2 ; [code] startup_menus: wait for editor_key bit 7 (mode menu)
var 0618:0401 overlay_ystep word ; [code] view_overlay_marks: row step of the current record
var 0618:0414 overlay_xstep word ; [code] view_overlay_marks: span-width step of the current record
```

`view_overlay_marks` records at DS:04EF + 4 × `view_not_forward` are as follows:
- a count byte (0 ends the list);
- word x step;
- a word whose low byte is the first `row_offsets` index − 2 and whose high byte is the start x;
- word y step;
- byte rows.

Each row fills `(x >> 8)` bytes of `overlay_fill` at `row_offsets[bl] + (int8)(y >> 8)`.
`overlay_fill` is cleared after each record, and the list continues only while the next record
starts at 0537.
