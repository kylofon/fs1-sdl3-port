# 3.22: retire the emulator

The default build now runs the game from boot to quit without the 8086 interpreter:
- `src/cpu8086.c` is not compiled into it;
- there is no emulated PIC, PIT, port I/O or BIOS;
- `--stats` counts 0 original instructions in every session.

What stays as plain data:
- `Cpu8086`'s register file and the 1 MB memory array. They are the natives' calling convention and data
  model.
- The CGA renderer, which still reads B800.

The interpreter, the emulated PC, the original boot loader, `--verify`, `--native-off` and `--trace` are in
the optional emulator build. `tools/verify_campaign.py` runs on that build and prints OK.

## Builds

| | default (`FS1_EMULATOR=OFF`) | emulator (`-DFS1_EMULATOR=ON`) |
|---|---|---|
| Sources | `cpu_core.c`, `pc.c` (machine as data), `sched.c`, `native.c`, natives | the same, plus `cpu8086.c` and the emulated hardware in `pc.c` |
| Runs | the C scheduler and the boot in C | the emulated PC (natives on), as before; `--csched` runs the default build's scheduler |
| Original code | none: reaching code without a native stops with an error (exit 3) | stepped by the interpreter (counted by `--stats`) |
| Options | play, `--frames`, `--keys`, `--screenshot`, `--stats`, `--list-natives` | also `--verify`, `--native-off`, `--trace`, `--csched`, `--emulate`, `--check-boot` |

    cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH=C:/msys64/mingw64
    cmake -S . -B build-emu -G Ninja -DCMAKE_PREFIX_PATH=C:/msys64/mingw64 -DFS1_EMULATOR=ON

The tools that run original code use `build-emu/` by default (`trace_campaign.EXE`), or the executable
named by `FS1_EXE`. `scripts/cloud_setup.sh` builds both. The cycle-table generators compile
`cpu8086.c` with the new `cpu_core.c`.

`cpu8086.c` was split:
- `cpu_core.c` (both builds): `cpu_read*`/`cpu_write*`, `cpu_push`/`cpu_pop`, `cpu_interrupt` and
  `cpu_reset`.
- `cpu8086.c` (emulator only): `cpu_step`. Its tables are now set up in `cpu_step`.

The natives' own calls into original code still name `cpu_step`. In the default build a stub of it in
`sched.c` stops the game with an error. No session reaches it.

## The C scheduler (`src/sched.c`)

`pc_run` calls `sched_run` when `pc->csched` is set. That is always the case in the default build; in
the emulator build it is set by `--csched`.

**Steps.** CS:IP always points at a native's address. That is the program body (the `start` blocks below,
then 3.21's main-loop blocks) or an interrupt handler. Each step:
- looks up the native at CS:IP (`native_step`, the CPU's pre-execution hook without the CPU);
- runs it. It charges the original's cycles, so `cpu.cycles` stays the game's clock.

**Interrupts.** Between two steps:
- **IRQ0.** It is raised every 4 × the divisor the game last wrote to PIT channel 0 (`sound_update` at
  0922, 3.19). The divisor is kept; nothing counts down. When the game reads a counter (it never does in
  the sessions), the value is computed from the clock.
- **IRQ1.** It is raised when a scancode from SDL is queued, at most one every 10,000 cycles, as before.
- **Delivery.** An interrupt is delivered when IF is set and nothing of the same or higher priority is in
  service. The PIC state is only the mask, IRR and ISR bits; the handler's EOI clears ISR. Delivery is
  `cpu_interrupt`: FLAGS, CS and IP are pushed and the vector is followed. So `int8_timer` and
  `int9_keyboard` and their IRET are unchanged.
- **BIOS vectors.** While a vector is still the BIOS's (before `hook_int8`/`hook_int9`), the BIOS timer
  tick (BDA 6Ch) is done in C, and keys are dropped.
- **Reboot.** The reset entry F000:E05B (Ctrl+Alt+Del) reboots: power-on state, then the C boot. Any other
  BIOS address is an error.

**Interrupts fall only between natives.** So the 3.11-3.21 interrupt hand-backs and declines are not
needed. Under `pc->csched` they are switched off in five places:
- `irq_due` in editor.c, keys.c and sceneryload.c;
- `irq_hand_back` in flight_motion.c;
- `entry_run` in sound.c.

In `mainloop.c`, `fits()` is always true, and the polling loops (key waits, crash delay, paused loop,
border and overlay loops) do at least one pass and at most up to the next event. `pc_irq_horizon`
returns the scheduler's horizon. In the emulator build all of these run as before.

**Calls out of a native.** Natives in 3.4-3.20 sometimes run a callee as original code ("natives off").
Those helpers now call `native_or_cpu_step()` (native.c). Under the C scheduler it runs the enabled native
at CS:IP. Otherwise, and always in the emulator build, it runs one original instruction. A native that runs
its own routine as original code (a rare path it does not implement) is recognised by entry and SP, and is
not dispatched to itself.

**Long steps.** Some natives run longer than a frame:
- a scenery area change is 1.45 M cycles (0.3 s);
- `draw_scenery` is 0.6-1.0 M cycles.

The timer ticks that fall due inside such a step are delivered right after it, each handler as its own
step, before `sched_run` returns. `main.c` now resyncs its frame clock only after 2 s behind (it was
0.25 s), so such a step is paid back over the next frames instead of shifting the timeline.

## Boot in C

`sched_boot` does what `tools/pc_loadstream.py` decodes: the boot sector at 7C00 and 0500, then the load
stream from track 1, through the B800 track buffer. It does this with the loader's own variables (in the
segment at 0000:0120), its stack words, its INT 13h frames and BDA 41h. Commands:
- 01/02 copy;
- 03 sets SS:SP, DS, `view_buf_seg` and calls `cga_program_regs`;
- 04 fills `area_tracks`;
- the end jumps to `start` with the registers and flags the loader leaves.

The original loader takes 8,510,338 cycles (1.78 s). The scheduler lets that time pass first, with the
BIOS timer ticking and the power-on text screen shown. Then it decodes the stream and starts the game at
the same cycle. So the menus come up at the same frame as with the original, and scripted sessions keep
their timing.

`fs1 --check-boot` (emulator build) runs the original loader and the C boot to `start` and compares them:
- registers, flags and cycles are identical;
- memory differs in 1 byte, 0C0A4. That is a stack word of an IRQ0 frame that the emulated BIOS timer
  pushed during the original's load.

The boot-sector disk code that `check_master_disk` runs at start-up uses 3.20's interpreter, with seven
new entries in sceneryload.c: `disk_error`, `disk_reset`, `disk_set_ds`, `boot_read_track`, `motor_off`,
`boot_stream_byte` and `boot_stream_word`.

**Blocks.** Code that waits for a key or never returns is split into blocks, as `main_loop` is (3.21):
- one function is bound at the entry and at every return address;
- a block runs to the next CALL, pushes the return address and sets IP to the callee;
- the callee is then the scheduler's next step.

Under `--verify` the blocks have stop ranges, so the original runs to the same point. Routines that return
are one call each, with their callees run nested.

**Cycles.** Cycles are the cpu8086.c cost of every original instruction, from `startup_cycles.h`
(`tools/gen_startup_cycles.py`).

## Sound

The engine note is the 3.19 model:
- `int8_timer` rotates `spk_pattern` into port 61h bit 1 on every IRQ0, at the rate the game programmed
  into channel 0;
- channel 2 tones come from `speaker_tone` / `sound_update`.

The port 61h and channel 2 writes go to the speaker log, and `pc_speaker_render` makes the audio from it
into the SDL stream. There is no emulated PIT behind it.

A timer tick can be delivered late, because a native is never interrupted. When it is, its handler's
speaker writes are stamped as if it had run on time (`speaker_bias`, set by the scheduler for the IRQ0
handler step). So the note keeps the programmed rate.

`python tools/audio_compare.py --csched` (new option) renders both builds' audio from the speaker events.
Compared per second of audio:

| Session | C scheduler vs original (natives off) | emulator, natives on, vs original |
|---|---|---|
| demo | level 1.1 %, pitch 0.9 % | level 62.5 %, pitch 6.0 % |
| flight_keys | level 0.6 %, pitch 1.0 % | level 62.2 %, pitch 7.3 % |

The figures are median differences per second; pitch is measured by zero crossings. The default build
sounds like the original game. The emulator build with natives is the outlier: its long natives hold the
timer, and the 3.21 IRQ0 backlog then delivers the ticks in bursts. That build is only for verification.

shows the blank power-on screen until it loads at the original's end time. Both continue identically.

## Remaining fallbacks

- **Disk backup.** `startup_menus` → `disk_backup` (5F54) is reached only with a master disk (track 1Ch
  byte 0 = 1) and C in the mode menu. It needs a second, blank disk. It has no native, so the default
  build stops there with the "no C implementation" error. The emulator build runs it as before.
- **BIOS services.** No session calls any (the 3.20 INT 13h natives do the disk reads). If one were reached,
  `sched.c` logs it and does nothing.
- **Unknown handler in `reliability_failure`.** Only the eight handlers at 05EF-0624 are done (AND
  [19A0] / OR [1DC8]); another target is logged.
- **Verification.** `--verify` and the trace tools need the emulator build. Under `--verify` (emulator
  build) everything runs as before, including the hand-backs.
